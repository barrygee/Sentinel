# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Sentinel is a real-time, offline-capable multi-domain surveillance dashboard (Air, Space, Sea, Land, SDR): a **FastAPI** backend serving a **Vue 3 SPA** that renders live data on **MapLibre GL** maps (**PMTiles** for offline tiles). The real frontend is the Vue SPA in `frontend/vue/`. `README.md` is current — it covers user-facing setup/features; this file covers working-on-the-code details.

## Develop & deploy

**Dev loop (hot reload — use this for frontend work).** Two terminals:
```bash
# 1. backend on :8080 (the port Vite's proxy expects — see frontend/vue/vite.config.ts)
docker compose up                 # core + every section + the radio hub, code volume-mounted, on :8080

# 2. Vite dev server with Vue HMR — open http://localhost:5173
cd frontend/vue && npm run dev    # proxies /api, /ws, /assets to :8080
```
Backend changes hot-reload via `uvicorn --reload` in each container; Vue changes via Vite HMR. No rebuilds.

**Deploy.** One command builds everything (multi-stage: compiles the SPA, packages the backend):
```bash
docker compose up --build -d      # app on http://localhost:8080
```
You only need `--build` when **dependencies** change (`pyproject.toml` / `package.json`). For plain code changes the volume mounts pick up backend edits live, and `cd frontend/vue && npm run build` regenerates the served `frontend/spa-dist/` (hard-reload the browser — no Docker restart).

**Multi-arch images.** `docker-bake.hcl`: `docker buildx bake` builds the backend image for linux/amd64 + arm64 (CI's `multi-arch-build` job builds it without pushing); `docker buildx bake decoders` builds the decoder images — local only, never pushed or built in CI (mbelib). The SPA stage runs on `$BUILDPLATFORM` (identical output per arch); keep it that way or arm64 builds compile the bundle under QEMU. Bake also reads `docker-compose.yml`, so its service names are targets too. Decoder upstreams are pinned to commit SHAs (`MBELIB_COMMIT`/`DSDFME_COMMIT`/`READSB_COMMIT`, fetched shallow by SHA) and Direwolf's tarball to a SHA-256 — move a pin by editing the Dockerfile ARG.

Note: `frontend/spa-dist/` (the built bundle) **is committed** and is what the backend serves in production — rebuild and commit it when shipping a frontend change.

## Test & lint
Run backend commands from the repo **root** (tests need `pythonpath=.`), and pass `--project backend` so uv uses the backend venv — the project's `pyproject.toml` lives in `backend/`, so a bare `uv run` from the root resolves to the wrong interpreter (an unrelated `~/.venv` / system pytest). If you get `ERROR: Missing required plugins: pytest-asyncio`, that is the guard in `pytest.ini` telling you pytest is running outside the backend venv — fix the interpreter rather than installing the plugin globally.
```bash
# Backend (root)
uv run --project backend pytest                                  # all backend tests
uv run --project backend pytest tests/backend/test_routers_air.py::test_name   # single test
uv run --project backend ruff check backend services/sections services/radio    # lint (conservative: E,F,I,UP,B) — GATING
uv run --project backend ruff format --check backend services/sections services/radio   # format check — GATING (ruff format is the Python formatter)
PYTHONPATH=. uv run --project backend lint-imports --config backend/pyproject.toml   # section import boundaries — GATING
uv run --project backend mypy backend                            # informational only, NOT gating (~90 known errors)

# Vue SPA (run from frontend/vue/) — the application
cd frontend/vue && npm run lint                                  # ESLint + Prettier --check
cd frontend/vue && npm run typecheck                             # vue-tsc --noEmit
cd frontend/vue && npm run test:coverage                         # vitest — GATED AT 100% coverage (CI fails on any drop)
cd frontend/vue && npm run test:e2e                              # Playwright + axe-core (frontend/vue/e2e/) — GATING
cd frontend/vue && npx playwright test e2e/sdr.spec.ts            # single e2e spec
cd frontend/vue && npm run test:e2e:report                       # open the last HTML report

# Web packages (platform/web/* + services/sections/*/frontend) — run from the repo root
npm run web-packages -- lint                                     # ESLint + Prettier --check, every package
npm run web-packages -- typecheck                                # vue-tsc / tsc
npm run web-packages -- test:coverage                            # vitest, 100% coverage gate per package
cd services/sections/sdr/frontend && npm run test:coverage       # one package

# Root tooling
npm run lint                                                     # ESLint + Prettier over root config files + tests/e2e specs
npm run typecheck                                                # tsc --noEmit over the same surface (root tsconfig.json)
npm run check:doc-links                                          # every link + #anchor in the /doc markdown resolves (scripts/check-doc-links.mts) — GATING
```
All of the above run in CI (`.github/workflows/ci.yml`) on every PR and push to `main`; ruff check + `ruff format --check` + import-linter + pytest (backend), ESLint/Prettier + vue-tsc + vitest@100% + Vite build + **Playwright/axe e2e** (SPA), and ESLint/Prettier + `tsc` + the doc link check (root) are gating.

**Don't forget the e2e suite.** `npm run test:coverage` passing is NOT enough to know CI will be green — the `frontend-vue / a11y (Playwright + axe-core)` job is a separate gate, and UI restructuring (renaming a rail tab, moving a section between a pane and an accordion, adding an ARIA live region) breaks it while every vitest spec still passes. Run `npm run test:e2e` before pushing any UI change. Two gotchas that cost real time: Playwright's **strict mode** fails a bare locator that matches more than one element, so adding a second `[role="status"]` region breaks an unrelated shell spec — use `.first()` when the intent is "at least one"; and the suite serves the **committed** `frontend/spa-dist/` bundle via `npm run preview`, so `npm run build` first or you are testing stale code. mypy is not. A **husky** pre-commit hook (`.husky/pre-commit` + `.lintstagedrc.json`) mirrors the format/lint gates on staged files across both npm contexts. `CHANGELOG.md` is regenerated automatically from Conventional Commits on every push to `main` (`.github/workflows/changelog.yml`, git-cliff), and committed back to `main` with `[skip ci]` — it never touches feature branches, so local checkouts don't diverge. Don't hand-edit it. See `CONTRIBUTING.md` for the full contributor workflow and conventions; new code is expected to ship at 100% frontend coverage.

## Two npm contexts — don't confuse them
One **npm workspaces** install at the repo root (single root `package-lock.json`, deps hoisted to the root `node_modules`; members: `frontend/vue`, `platform/web/*`). Run `npm install`/`npm ci` from the root; add an app dep with `npm install <pkg> -w frontend/vue`. The contexts below are about *which config and scripts apply*, not separate installs.
- **`frontend/vue/`** — the real app (Vite + Vue 3 + Pinia + vue-router); tested with **vitest** (100% coverage gate) + ESLint/Prettier + `vue-tsc`, **plus the Playwright/axe e2e suite in `frontend/vue/e2e/`**.
- **Repo-root `package.json`** — root-level tooling only: ESLint/Prettier over config files + the full-stack e2e specs in `tests/e2e/`, plus husky/lint-staged. Not the app build.

## Two SEPARATE e2e suites — check both
There are two, in different directories, run by different tooling. Finding one and assuming it is the only one is a live trap:
- **`frontend/vue/e2e/`** — the big one (21 spec files, 158 tests: shell, sidebar, settings, settings-routes, notifications, connectivity, scaffolding, a11y, offline-maps, sentry-sites, air, space, sea, land, sdr + sdr-radio-switch/sdr-engine-late-mount/sdr-css-cascade, the P0 parity specs (SDR audio survives navigation, notification click-through) and remote-down; `npx playwright test --list` from `frontend/vue/` prints the current count). Playwright + `@axe-core/playwright`, config `frontend/vue/playwright.config.ts`, run via `npm run test:e2e` from `frontend/vue/`. **This is the gating CI job**, and it is where UI-structure assertions live (rail tab ids and counts, `aria-controls` targets, live regions).
- **`tests/e2e/`** — the full-stack smoke spec plus `gateway-smoke.spec.ts`, config `playwright.fullstack.config.ts` at the repo root, driven by the root `package.json`. There is no server-starting mode: `npm run test:e2e:gateway` drives an already-running `docker compose up` stack on :8080 through Caddy (`SENTINEL_E2E_BASE_URL`) and is the gating `gateway-smoke` CI job — a 3-leg matrix, each starting a different set of section containers (the app never hosts a section under compose): `sections-service` — Space, Land, Air, Sea, SDR and the radio hub, as `docker compose up` runs them; `sections-absent` — only the SDR container, so the shell has a section; `sdr-absent` — everything but SDR, so the shell boots without its eager audio engine; `section-deployment.spec.ts` reads `SENTINEL_E2E_SECTIONS` (e.g. `space:service,land:absent,air:service,sea:service`; unlisted = `service`, parsed by `tests/e2e/support/sectionDeployment.ts`) and runs its checks per extracted section (the "other sections keep working" checks use whichever default-enabled sections the leg deploys), and the Space/SDR-specific smoke checks skip when that section is absent. Land ships disabled, so its view check enables it via the settings API and restores it.

## Architecture

**Gateway (`gateway/caddy.json` + `backend/core/gateway_routes.py`/`gateway_sync.py`).** Under Docker, Caddy (`gateway` service) publishes :8080 and the app is internal-only (`app:8000`). Its static config does three things only: `/internal/` → JSON 404 (never routed — remember GET `/internal/**` on bare uvicorn falls through to the SPA), everything unmatched → app, proxy failure → JSON 503 (`handle_errors`). All section, radio hub and `/remotes/<id>/` prefixes are **pushed at runtime from the service registry** into the `registry_routes` subroute via Caddy's admin API (:2019, compose network only): a reconcile loop in core GETs it back and PATCHes when it differs, woken by `registry.changed` and every `GATEWAY_SYNC_INTERVAL_S` (so a restarted gateway heals itself). Longest prefix first — `/api/air/messages` (core) beats `/api/air/`, `/api/sdr/radios` (hub) and `/api/sdr/adsb/` (Air) beat `/api/sdr/`. A registry-unavailable service gets a static 503 without dialling. Empty `GATEWAY_ADMIN_URL` (the test app) = no gateway. Caddy flushes SSE and proxies WebSockets with no extra config; don't add buffering. The shell's CSP is set by the **app** on `index.html` (`backend/core/spa_csp.py`, inline boot scripts allowed by hash computed from the file on disk) — it keeps `blob:` + `'unsafe-eval'` because SDR audio needs them (blob worklet; `new Function` ScriptProcessor fallback on plain-HTTP LAN).

**Serving model (`backend/core/app.py` + `backend/core/spa_serving.py`).** FastAPI is the only app server. `backend/main.py` is just core's uvicorn target: `create_core_app()` builds **core only** — notifications, settings, offline maps, `app` (`GET /api/app/sections` lists the registry's sections with a built remote, `backend/core/app_sections.py`), `/internal/registry/register` (service registration gated by each service's own credential, `backend/core/registry_router.py`; `backend/core/service_registry.py` health-probes every registered service), secret settings, `/health` → `/assets/**` (tiles/sprites/fonts) → `/spa-assets/**` + `/fonts/**` (hashed Vue bundle) → `/remotes/**` (a 404 from core: each section serves its own Module Federation remote, `remoteEntry.js` `no-cache`) → `/{full_path:path}` catch-all serving SPA `index.html` (`no-cache`, so it never pins a stale bundle) for vue-router. **Every built file must live under one of those mounts** — anything else at the site root falls through to `index.html` and fails as a module script with a text/html MIME error (why the shell's federation entry is `spa-assets/remoteEntry-[hash].js`). No part of `backend` may import a section (import-linter); each runs as its own service, the way `create_service()` composes it. **The backend tests run an all-in-one app** (`tests/in_process_app.py`, imported by the root `conftest.py`): `create_core_app()` given every section's and the hub's routers (interleaved under `/api/sdr/` in the original order — the route-inventory golden pins it), their lifecycles in order and in-process registrations. No deployment runs it. `lifespan` runs each module's `ModuleLifecycle` (core's `bus`+`core` in `backend/modules/`, each section's `sentinel_<id>.module`; runner in `backend/platform/lifecycle.py`): every module's `prepare` (tables, migrations, seeders) before any `start` (config-file sync, offline-map runner, resumed decodes, Sentry poller, Land's 24h cleanup loop, AIS reader), `stop` in reverse — and **chains SIGTERM/SIGINT** to every module's `wake` hook (SDR WS queues, decode bridges, AIS reader, offline-map job runner) before uvicorn shuts down — without it, long-lived SDR WS tasks and a running `pmtiles extract` subprocess deadlock `--reload`. Don't remove that. Notifications (`/api/air/messages*`, every section's alerts despite the path) are core: `backend/core/notifications.py`. A section raises a **server-side** alert by publishing `notifications.raise` on the bus; core stores it and pushes it over SSE (`GET /api/air/messages/stream`, opened once by the notifications store from `App.vue`). Emergency squawk alerts (7700/7600/7500) work this way (`sentinel_air.services.adsb_squawk`, plan `docs/plans/adsb-server-alerts.md`): every snapshot Air fetches feeds a squawk tracker, and an idle-only watcher fetches around the receiver/location when no browser is polling — so `AdsbLiveControl` only highlights emergencies and must not raise squawk alerts itself. **Radio hub (`services/radio/backend/`, package `sentinel_radio`)** owns everything that touches a physical radio — rtl_tcp/Sentry IQ, radio CRUD, connect/status, all four `/ws/sdr/*` sockets, the decode bridges and their `/api/sdr/{decode,aprs,ais}/*` routes; the SDR section router (`sentinel_sdr.router`) keeps frequencies, groups, search ranges, band plan and recordings. They share `/api/sdr/`; the gateway's longest-prefix match keeps them apart.

**Section backend packages (`services/sections/<id>/backend/`; the radio hub, which is not a section, at `services/radio/backend/`).** A moved section is the package `sentinel_<id>` (`router`, `services/`, `models`, `database` — its tables, ALTERs and seeders —, `module` — lifecycle + manifest —, `service` — its `uvicorn sentinel_<id>.service:app` entry point) with its tests in `tests/` beside it (on pytest's `testpaths`; the root `conftest.py` applies). It is an editable **path dependency** of `backend/pyproject.toml` (`[tool.uv.sources]`), so `uv run --project backend …` and the one image see it like any package; its own `pyproject.toml` only names it and extends the backend's ruff config. Moving a section also means: an entry in `_MOVED_MODULES` (`backend/modules/__init__.py`), its models imported in the root `conftest.py`, its name in import-linter's `root_packages`, a `COPY` of its `pyproject.toml` (lock check) and of its folder (install) in `backend/Dockerfile`, and a live-reload bind mount of only its backend folder on its compose service. Core no longer creates a moved section's tables — its `module.prepare` does. The radio hub's package `sentinel_radio` has the same layout (plus `radios.py` and a `routers/` folder) and the same wiring.

**Section services (P6–P8, `backend/platform/sdk/` + each package's `service.py`; decision record `docs/adr/0006-section-containers.md`, operator guide `docs/operations.md`).** Each section runs as its own service: same image, `uvicorn sentinel_<id>.service:app` (`sentinel_radio.service:app` for the hub), built by `create_service()` from its package's routers, lifecycle and manifest. **Space** (service `space`; own DB `space.db` on `space_data`) **Land** (service `land`; `land.db` on `land_data`; APRS packets reach it as `decode.aprs.*` from the radio hub over NATS, so it needs `nats`) and **Air** (service `air`; `air.db` on `air_data`; owns `/api/air/` + `/api/sdr/adsb/` but core keeps `/api/air/messages`; Sentry reservation / receiver-location requests to the hub and squawk alerts (`notifications.raise`) go over NATS; the `adsb-decoder` polls `/api/sdr/adsb/config` **through the gateway** so it finds Air wherever it runs) and **Sea** (service `sea`; `sea.db` on `sea_data`; holds the one AISStream connection a key allows; the AISStream key is a secret the public settings API redacts, so Sea reads it through the settings client's `read_secret` → core's `/internal/settings/secrets/{ns}/{key}`, limited to `SECRET_SETTING_KEYS` and to the owning service's credential) — each copied from `sentinel.db` on first boot by `legacy_import.py`; section services share the `x-section-service`/`x-section-env` compose anchors. It registers with core over `/internal/registry/register` (with its own HTTP credential, see Internal credentials below) and its registration routes `/api/space/` + `/remotes/space/` to it in the gateway — no other switch. The **radio hub** extracts the same way (`sentinel_radio.service`, service `radio`, `radio.db` holding only `sentry_hosts`; radios and the APRS/AIS radio ids stay core settings, read through the settings client; no UI remote) plus two deployment specifics: decoders reach the hub through the gateway (`SENTINEL_GATEWAY_URL`, default `http://gateway:8080`) and learn its PCM/voice-audio sockets from each `/config` reply (`pcmFeed`/`voiceAudioReturn`, host = the address the hub registered — `sentinel_radio/services/decoder_sockets.py`), so nothing says which container hosts it; and IQ captures are written into the hub's staging `iq-captures/`, which the SDR section collects over HTTP (`sentinel_sdr.services.sdr_iq_capture_transfer`: a background copy on stop — the recording reads `iq_file_pending` until it lands — plus a 60 s reconcile loop that retries, stops stray captures and has the hub discard uncollected ones via `hub.iq-capture.{locate,list,discard}`; the file comes from the hub's `/internal/radio-hub/iq-captures/<id>` (the one place the old `radio-hub` name survives: the route-inventory golden pins it), which only the SDR section's credential may fetch, never gateway-routed), so no volume is shared (P7.3). The **SDR section** (`sentinel_sdr.service`, service `sdr`, `sdr.db` + `recordings/` on `sdr_data`) is the last: it serves only the rest of `/api/sdr/` — the hub's and Air's longer prefixes win in the gateway. Recordings are saved under `RECORDINGS_DIRECTORY` (`/recordings` under compose: the `sdr_recordings` volume or the host folder `SENTINEL_RECORDINGS_DIRECTORY`) in the subfolder the `sdr.recordingsFolder` setting names — validated as a relative subfolder (no absolute/`..`/backslash, still inside the root after resolving symlinks), falling back to the root — and **each recording stores its folder** (`SdrRecording.directory`, `""` = legacy `recordings/` beside `sdr.db`), so changing either never strands old files; always go through `sentinel_sdr.services.recording_folders` (`wav_path`/`iq_path(recording)`), never build a recordings path by hand. Legacy import copies its five tables **and** the WAV/`.u8` files of the recordings it copied (`import_legacy_files`, only on the boot that imported `sdr_recordings`). Its settings mirrors (`sdr.groups`/`frequencies`/`searchRanges`, written after every edit so the config file shows them) and `sdr.bandPlan` (the waterfall reads it from core) go through the settings client. **Every deployment runs all six as services** (P8: there is no in-process hosting and no non-Docker dev loop — `docker compose up` is the way to run Sentinel; leave one out with `--scale <service>=0`, or `SENTINEL_RADIO_REPLICAS=0` when the hub runs on a radio host). Core **never even imports** a section's code (`tests/backend/test_core_entry_point.py` checks it in a fresh interpreter), because sections subscribe to bus events at import (Land's `decode.aprs.*` store) and the hub registers `hub.*` responders — a copy in core would handle what is meant for the service. Settings stay in core: with `SENTINEL_CORE_URL` set, `platform/settings_client.py` (and `resolve_domain_urls`) go over HTTP to core's `/api/settings` — so section code must read/write settings through the settings client, never `user_settings` directly. Because a section's settings are core's, `create_service()` **holds every service's startup until core answers** (`wait_for_core` in the settings client, run as the first `prepare`, before any section `prepare`/`start`) — a `docker compose up` starts sections before core, and their first cleanup/watchdog/backfill used to fail once and log a traceback. It logs `<id> service startup: waiting for core to answer (…)` while waiting and `… connected to core at <url> [after N s]` once core answers. New sections get this for free; don't add per-loop waits. Tests run with an autouse `core_is_up` fixture (root `conftest.py`) that makes the wait a no-op. A section's module must import no other section's (`TestImportedAlone` in `test_modules_lifecycle.py`), or the hub's `hub.*` responders would answer locally in the section container instead of over NATS.

**Radio host / multi-host (P7.5, `compose.radio-host.yaml`, `docs/radio-host.md`).** The hub and decoders can run on a second machine. Everything crossing the LAN is TLS with the deployment CA: the core gateway's second listener **:8443 is the service entrypoint** (`gateway/caddy.json` `service_entrypoint`, every path → `app:8000`, `/internal/` included — published on 127.0.0.1 unless `SENTINEL_SERVICE_ENTRYPOINT_ADDRESS`; cert in `credentials/gateway/` for `gateway`, `localhost`, `SENTINEL_CORE_HOSTNAMES`, which also feeds the NATS cert — renamed from `NATS_SERVER_EXTRA_HOSTNAMES`), NATS is published via `NATS_PUBLISHED_ADDRESS`, and the radio host's `radio-host-gateway` Caddy (`gateway/radio-host-caddy.json`) fronts its hub with a cert core issues when `SENTINEL_RADIO_HOST_HOSTNAMES` is set (the CA key never leaves core). Internal HTTP clients (settings client/`wait_for_core`, registration, registry probes, IQ-capture transfer) verify with `backend/platform/internal_tls.py` (`INTERNAL_CERTIFICATE_AUTHORITY_FILE`: certifi + the deployment CA); the gateway trusts the CA for `https://` upstreams via `GATEWAY_UPSTREAM_CERTIFICATE_AUTHORITY_FILE` (a path in the gateway container, `gateway_routes.py`). The gateway runs as the runtime uid (it reads the 0600 key). A hub behind a radio-host gateway sets `DECODER_SOCKETS_HOST=radio` so config replies send decoders to it over the local compose network (no PCM on the LAN); radio-host decoders use `SENTINEL_GATEWAY_URL=http://radio:8000`. Credentials move with `backend/scripts/service_credentials_bundle.py` (`export radio-host` on core via `docker compose run --rm -T service-credentials …`, `credentials-import` one-shot on the radio host; refuses `core`/`gateway`, validates every tar member). Sentry hosts are in the hub's own DB, so a new radio host starts with none.

**Event bus (`backend/platform/bus.py` + `nats_transport.py`).** Sections talk through NATS-shaped subjects (`settings.changed.<ns>`, `decode.<kind>.<radioId>`, `hub.*` request/reply — plan §3.3), never by importing each other. `publish()` awaits every **local** handler synchronously (settings side effects and `raise_errors=True` call sites rely on it), then, when `NATS_URL` is set (`backend/modules/bus.py`, first in `MODULES`), forwards to NATS for other processes; `request()` uses a local responder if one exists and only otherwise goes over the wire. Payloads cross as JSON: the process-local `db` session is stripped on the way out and the receiver injects its own, so handlers keep their signatures; a remote responder's exception comes back as `RemoteHandlerError`. Connections use `no_echo` (local handlers already ran — don't remove it or every event is handled twice). An unreachable broker never blocks startup or a publisher. Never put FFT/IQ/PCM on the bus. Under Docker the broker is TLS-only (a CA generated per deployment) and every process signs in as its own NATS user (`core` for the app, else the service id) allowed only the subjects in `backend/platform/nats_permissions.py`: the one-shot `service-credentials` service (`backend/scripts/generate_service_credentials.py`) writes the CA, server cert, per-service `nats-credentials.json` and `nats.conf` onto the `service_credentials` volume, and each service mounts only its own `credentials/<user>/` folder (named `credentials/`, not `services/`, so no volume folder shares a name with a repo folder) (`NATS_CREDENTIALS_FILE`, `NATS_CERTIFICATE_AUTHORITY_FILE`; requests reply on `_INBOX.<user>`). **A new subject must be added to that table**, or the broker refuses it (the service logs a NATS permissions violation and the event stays in-process); after a table change, `docker compose restart nats`.

**Internal credentials (P7.4b, `backend/platform/service_access.py` + `service_credentials.py`).** There is no shared join token or decoder secret: the same `service-credentials` run gives every service and every decoder (`voice-decoder`, `aprs-decoder`, `ais-decoder`, `stub-decoder`) its own random token in `credentials/<caller>/http-credentials.json` (`SERVICE_HTTP_CREDENTIALS_FILE` / the decoders' `DECODER_CREDENTIALS_FILE`), and writes core and the radio hub an `accepted-callers.json` (`ACCEPTED_CALLERS_FILE`) mapping each token's **SHA-256 hash** to its caller — neither holds anyone's token. Services send theirs as `Authorization: Bearer`, decoders in `X-Decode-Secret` (header name kept: the OpenAPI golden pins it). The guards are `backend/core/internal_auth.py` (`require_caller` → 503 with no list, 401 unknown; `require_permission` → 403; `require_decoder`), and `service_access.py` is the table of what each caller may do: register only its own id, read only its own secret settings (only `sea` → the AISStream key), fetch IQ captures (only `sdr`), act as a decoder of its own kind only. `core` passes every check except the decoder one. **A new service or decoder kind must be added to that table** (and given a compose mount of its `credentials/<caller>/` folder), or it can't authenticate. With neither file set (the test app, unless a test sets them), internal routes and decoder endpoints answer 503.

**Offline map downloads (`backend/routers/offline_map.py` + `backend/services/offline_map/`).** Settings › App Settings › Offline Maps lets an operator pick a bbox + depth (max zoom 6–14) and download Basemap and/or Terrain for offline use, on top of the bundled `uk.pmtiles`/`uk-terrain.pmtiles`. Extraction shells out to the go-pmtiles CLI (`pmtiles extract`, bundled in `backend/Dockerfile`) against the Protomaps planet build (the newest v4 build, found automatically from Protomaps' `builds.json` by `basemap_source.py`, since dated builds are deleted after about a week) or the Mapterhorn DEM, one job at a time via a single-worker queue started in `lifespan`. Regions are rows in `offline_map_region` (SQLite) plus `<uuid>.pmtiles` / `<uuid>.terrain.pmtiles` archives under `resolved_offline_tiles_dir()`. Two resolver endpoints — `GET /api/offline-map/basemap/{z}/{x}/{y}` and `.../terrain/{z}/{x}/{y}` — serve tiles by checking completed regions newest-first, then the bundled base archive, then 204; `tile_tier_resolver.py` caches open pmtiles readers across requests. The offline basemap styles (`fiord.json`/`osm-light.json` — LIGHT is OpenStreetMap's default palette, generated from the dark pair by `frontend/scripts/build_light_basemap.py`) and `terrainDem.ts`/`TerrainToggleControl.ts` read from these endpoints instead of opening `.pmtiles` files directly. **`tiers_version` (from `/api/offline-map/status`) is what drives a live map refresh when a download completes** — `useOfflineTierRefresh` calls `(source as VectorTileSource).setTiles([...])` with a `?v=` cache-buster, never `map.setStyle()`: `setStyle` in diff mode doesn't refetch a source whose `tiles` array is unchanged, and a full restyle wipes overlay layers. Don't reintroduce a `setStyle` call here.

**Domains.** `air` (ADS-B), `space` (SGP4 + day/night terminator), `sea` (AIS via AISStream), `land` (APRS via Direwolf, UK repeater directory from ukrepeater.net cached daily in `repeater_cache` with a bundled `backend/data/uk_repeaters.json` fallback (`backend/scripts/refresh_repeaters.py` regenerates it) — `backend/services/repeaters.py`), `sdr` (RTL-SDR spectrum) are implemented. Sea additionally decodes AIS off-air off grid (`ais-decoder` sidecar). vue-router gates routes by `appStore.enabledDomains`.

**Sea / AIS pipeline (`sentinel_sea.services.ais_stream` + `ais_store`).** One AISStream WebSocket per process (the upstream allows one per key), driven by a watchdog that reports silence fast (2 min) but recycles/reconnects slowly (back-off ladder, 15-min DOWN retry, hourly auth probe) — do not "fix" the slow ladder, a reconnect storm locks the key out. Vessels live in an in-memory dict keyed by MMSI (static data merged in, 30-min retention, per-vessel track deque) and are snapshotted to `sea_vessel_cache` every 30 s for warm starts. The AISStream key is a secret: it is redacted/refused by the generic settings router (`_SECRET_SETTING_KEYS`) and only reachable via `/api/sea/ais-key`. On the map, `AisVesselsControl` pushes GeoJSON at most once a second and only when the source reports `loaded()` — a faster `setData` cadence starves MapLibre's single worker and the whole map stops painting.

**Sea has TWO sources feeding ONE store.** Off grid, vessels come from the SDR AIS decoder instead of AISStream: `sentinel_sea.services.ais_decode` maps a decoded sidecar event onto the *AISStream-shaped envelope* `AisVesselStore.ingest_envelope` already takes, so everything downstream (snapshot, tracks, ship-type classification, `sea_vessel_cache`) is identical whichever source is live — don't add a second ingest path to the store. The Sea router picks the feed with `resolve_effective_mode("sea", db)` and must **never call `reader.ensure()` off grid**: there is no internet to reach AISStream on, and the attempt burns the reconnect ladder and logs auth probes forever. Both sources report the same status shape, with `mode` saying which one. The off-grid source is a radio, not a URL, which is why `NoUrlOverlay` accepts a designated `sea.aisSdrRadioId` in place of an off-grid URL.

**Connectivity.** Each domain has online + offline source slots; a global `connectivityMode` plus per-domain `sourceOverride` (online/offgrid — there is no 'auto'; picking the global mode sets every domain to it, and a legacy 'auto' is converted at startup) select the active one. `resolve_domain_urls()` in `backend/utils.py` centralises this and returns `(primary, fallback)`. For domains whose sources are not URLs (Sea: an AISStream WebSocket vs a local SDR decoder) `resolve_effective_mode()` applies the same precedence and just returns the mode.

**Caching.** `backend/cache.py` (`now_ms`/`is_fresh`/`is_within_stale`): SQLite write-through with a fresh TTL and a longer stale window (serve old data if upstream fails). ADS-B returns `X-Cache: HIT|MISS|STALE`. TTLs in `backend/config.py` (Pydantic Settings, env/`.env` overridable).

**Persistence.** SQLite + SQLAlchemy 2.0 async. Schema built from ORM models on startup; defaults and SDR band-plan/frequency/satellite-radio data seeded from `backend/data/*.json`. Prefs live in `user_settings` as `namespace/key/JSON-value`. **Every setting is mirrored live to `backend/data/sentinel_config.json`** (git-ignored; `APP_CONFIG_PATH` overrides): `services/app_config_file.py` hooks SQLAlchemy commits to rewrite it on any `user_settings` change, and polls it (polling, because inotify doesn't cross Docker Desktop bind mounts) to apply hand-edits through the same `apply_config` as the Settings upload — the SPA's `useConfigFileSync` then refreshes the app's settings in place on `external_edit_at`. **Nothing reloads the page for settings**: APPLY CHANGES and config-file edits both call `refreshSettingsFromBackend` (`frontend/vue/src/shell/applySettings.ts` — the same `applySettingsPayload` boot runs, then `sentinel:config-uploaded`), so anything that loads a setting once (on mount, at start) must also re-read it on `sentinel:config-uploaded`, or it goes stale until the next full load. A new setting must be added to `backend/default_config.json` (seed + canonical key order) or it won't appear in the file until first written. Tests use an in-memory StaticPool engine, override `get_db`, and skip lifespan (`conftest.py`), and run against the code's defaults: the root `conftest.py` re-initialises `settings` without the repo `.env` before importing the app, so a live `.env` (e.g. `GATEWAY_ADMIN_URL`, `NATS_URL`) can't change the parity goldens. Real environment variables still apply.

**Decode bridges (`sentinel_radio/services/sdr_decode.py`).** One FM-demod PCM spine (`PcmDecodeBridge`) serves three sidecar kinds over three TCP ports — voice/dsd-fme (7355), APRS/Direwolf (7357), AIS/Direwolf (7358) — with one registry each, so starting one never disturbs another and all three can decode concurrently on three dongles. APRS and AIS additionally **own an absolute channel** (`ChannelOwningDecodeBridge`): they tune the dongle on start, re-derive their demod offset from the centre frequency each chunk was actually captured on (so a viewer retuning *within* the span is harmless), and pull the radio back after ~15 s when something moves the span off channel. AIS is the only **stereo** bridge — it owns two channels 50 kHz apart and interleaves them (left = A, right = B) for a two-channel Direwolf, because decoding one loses half the traffic. **New decoder kinds need no hub code** (only an entry in `service_access.py` for its credential): a container registers a manifest (`POST /api/sdr/decoders/register`, `sentinel_radio/services/decoder_manifest.py`) and the hub runs a generic bridge for it (`manifest_decode.py` — `ownership: absolute` gives `ChannelOwningDecodeBridge` semantics, two channels give stereo), starts/stops it via `/api/sdr/decoders/{kind}/*` or `hub.decode.<kind>.*` on the bus, and publishes its ingested events as `decode.<kind>.<radioId>`. Registration is in memory; a decoder whose `/config` poll gets 404 registers again. The **stub decoder** (`decoder/stub/`, compose profile `decoder-stub`) follows that contract without decoding anything, and `tests/backend/test_decoder_stub_contract.py` runs it against the real app in CI (no mbelib, no radio).

**SDR pipeline (`sentinel_radio/services/sdr.py`).** Each radio connects to a remote `rtl_tcp` over raw asyncio TCP. **One broadcaster task per radio** reads IQ and fans FFT frames to all subscribed WS queues — avoids the `readexactly()` concurrent-reader error. Reads are sized **by time (~40ms ≈ 25fps)**, not sample count, so frame rate is stable when bandwidth changes. `rtl_tcp` cmd frame = 5 bytes `[cmd][big-endian uint32]`. FFT size clamped 1024–32768 (read the comments before changing).

**Shared web packages (`platform/web/`).** npm workspace packages the SPA imports from source (no build step): `@sentinel/ui` (`Base*` primitives incl. `BaseFilterPanel`/`SettingsDropdown`/`LabelFieldsTable`, `IconRail*`, generic icons incl. `AprsSymbol`, `overlays/` (`NoDataOverlay`, `MapNoticeBanner`), DOM composables — depends on nothing but Vue; import as `@sentinel/ui/base/BaseButton.vue`, `@sentinel/ui/composables/useDocumentEvent`) and `@sentinel/shell-api` (the shell↔section contract: registries + capabilities under `shell/*`, the core Pinia stores `app`/`settings`/`theme`/`basemap`/`notifications`/`offlineMaps`/`sentrySites`/`tracking` + `_persist`, `settingsApi`/`offlineMapsApi`, the `settings/` kit sections build their settings from (`useStagedSetting`, `BaseToggleSetting`, `BaseNumberSetting`, `JsonDataControl`, `OnlineSourceControl`, `SourceOverrideControl`, `RadioSelect`), `overlays/NoUrlOverlay`, `useConnectivity`/`useSidebarPaneTarget`, and the `testing/fakeRadio` spec double — import as `@sentinel/shell-api/stores/app`; `frontend/vue/src/stores/` now holds only section stores) `@sentinel/map-kit` (`MapLibreMap.vue`, `SentinelControlBase`, the shared map controls under `controls/*` — names, roads, terrain/`terrainDem`, sentry-sites, range-rings, map-zoom — plus sprites, map-cluster/map-label helpers, the map composables `useOfflineTierRefresh`/`useBasemapLayerSync`/`useMapContextMenu`/`useRangeRingOrigin`/`useUserLocation` and the map utils; import `.vue` with extension, `.ts` without, e.g. `@sentinel/map-kit/controls/terrain/terrainDem`) and `@sentinel/web-config` (shared tsconfig base, ESLint, Prettier, Vitest config + test setup). Each package has its own `lint`/`typecheck`/`test:coverage` (100% gate), run in CI by the `web-packages` job (`npm run web-packages -- <script>`). Package code uses relative imports — never the SPA's `@/` alias. Dependency direction: `ui` ← `shell-api` ← `map-kit` ← SPA; no package imports a section. Each section's UI is a Module Federation remote the shell loads at runtime from `/remotes/<id>/` (P4).

**Section packages (`services/sections/<id>/frontend/`).** Each section (air, space, sea, land, sdr) is its own workspace package, `@sentinel/section-<id>`: its views, map controls (`src/controls/<feature>/`), stores (`src/stores/`), composables, services, settings controls and `src/section.ts` (its registration with the shell). Each has its own `lint`/`typecheck`/`test:coverage` (100% gate); run every web package with `npm run web-packages -- <script>` from the root (`scripts/web-packages.sh`). A section imports only `@sentinel/{ui,shell-api,map-kit}` and itself — never another section or the SPA (lint: `noSectionImports` from `@sentinel/web-config/eslint`).

**Frontend shell (`frontend/vue/src/`).** The SPA is now the shell: App, router, `MapSidebar`/`SettingsPanel`/notifications chrome, and `shell/sections.ts` — the composition root and the only non-spec file allowed to import `@sentinel/section-*`. Section state lives in each section package's stores; cross-cutting core stores live in `@sentinel/shell-api/stores/*`; `_persist` (`@sentinel/shell-api/stores/_persist`) backs selected state with localStorage, reconciled against the backend on load. **State that must survive teleport remounts (pane/tab selection) belongs in the store, not component refs.** **Settings is a page** (`/settings/<section>`, `frontend/vue/src/router/settingsRoute.ts`): going to it leaves the current section like a section link (its view unmounts; the SDR engine, outside `<RouterView>`, plays on) and shows the same full-screen Settings panel; closing returns to the section it came from (`settingsReturn`). The settings store stays the panel's source of truth — `useSettingsRouteSync` keeps it and the URL in step both ways, so every existing "open settings" call moves the URL. A settings route keeps `body[data-domain]` of the section it came from (no `sentinel:domain-changed`). **Docs are a page too** (`/doc/<path>`, `frontend/vue/src/router/docsRoute.ts`, code in `frontend/vue/src/docs/`, opened from the Docs entry at the bottom of the Settings rail or a setting's `docPath` link; closing returns via `docsReturn`): the markdown in `docs/` (minus `docs/plans/`) plus `CONTRIBUTING.md` is bundled at build time with `import.meta.glob` (`?raw`), its menu is `docs/nav.json`, and it renders with markdown-it (`html: false`) → DOMPurify, Mermaid diagrams lazily (`securityLevel: strict`, SVG sanitised). Docs search and Settings search share one matcher, `frontend/vue/src/search/textSearch.ts` (Settings: every word must appear, source order; docs: any word, more matched words first, then field weight and whole-word over partial; synonyms in `docs/search/synonyms.ts`, whole words only). Heading anchors come from `markdown/headingAnchors.ts`, which `npm run check:doc-links` imports too, so CI and the page can't disagree. A new docs page needs an entry in `docs/nav.json`; editing docs changes the bundle, so rebuild and commit `frontend/spa-dist/`, and `docker compose up --build` is needed for the live stack (the image copies `docs/` + `CONTRIBUTING.md` into the SPA stage). Map features are class-based MapLibre `IControl`s under `services/sections/<id>/frontend/src/controls/<feature>/` (or `@sentinel/map-kit`'s `controls/` when several maps share one) extending `SentinelControlBase` from `@sentinel/map-kit` — add features as controls, not inline in the view.

## Conventions
- **Always work on a feature branch — never commit directly to `main`.** Before starting any new feature, fix, or edit (frontend, backend, or project config), create a branch off `main` (e.g. `feat/sdr-recording`, `fix/adsb-filter`, `chore/update-deps`). One branch per logical change; open a PR to merge back. This applies to every change, however small.
- Run all `uv` commands from the **repo root** with `--project backend` (see Test & lint for why).
- ruff lint is intentionally minimal (`E,F,I,UP,B`); `ruff format` IS gating; mypy is informational, not CI-gating.
- **Section boundaries are structural and lint-enforced.** Each section is its own package, so it cannot reach the SPA (no `@/` alias); `noSectionImports` (`@sentinel/web-config/eslint`) fails `npm run lint` when any package or the SPA imports `@sentinel/section-*`. Cross-section needs go through the shell's registries and capabilities (`@sentinel/shell-api/shell/*`). Only the SPA's `shell/sections.ts` (the composition root) and SPA specs are exempt.
- Frontend coverage is gated at **100%** (`frontend/vue/vitest.config.ts`) — new SPA code ships with tests that keep every threshold at 100, and every component ships a `jest-axe` accessibility test. Use `/* v8 ignore start … stop */` (not the single-line `next` form, which this vitest setup ignores) for genuinely unreachable defensive branches, with a reason.
- Conventional Commits are load-bearing: `CHANGELOG.md` is generated from them — don't hand-edit it. Branch off `main`; never commit to `main`. See `CONTRIBUTING.md`.
