# 0008. Request guard: fastapi-guard on every service, deny by default

Date: 2026-10-26
Status: accepted

## Context

Sentinel had no inbound protection beyond the gateway refusing `/internal/` and the credential checks on internal and decoder routes. There was no per-client rate limit, no ban for a client that keeps attacking, no detection of injection attempts, and no security headers on API responses. Any client that could reach :8080 could call any route a browser could: a script on the LAN, another website through a visitor's browser, or a decoder container calling the browser API.

Two facts made per-client protection impossible as things were:

- **The services never saw the real client.** Every request arrived from the gateway's container address, and uvicorn's proxy-header default didn't trust it. Rate limits and bans by address would have treated all clients as one, and banned the gateway.
- **There are eight FastAPI processes.** A ban or a counter kept in one process's memory doesn't apply to the others.

The owner asked for complete coverage of fastapi-guard's features, fitted to Sentinel and documented. Remote clients must also be unable to call endpoints they have no need to call.

## Decision

- **fastapi-guard 8.1.2 on every service.** It is installed by the two composition roots (`create_core_app`, `create_service`) through `backend/platform/security/`. With a deny-by-default access layer of Sentinel's own, it covers rate limits, auto-bans, attack detection, scanner blocking, security headers, request checks and behaviour rules.
- **One policy file, `backend/security/guard-policy.json`, validated strictly.** Each section sets behaviour per process profile. Unknown keys stop startup, because fastapi-guard's own config only logs them. Secrets and per-deployment addresses come from `GUARD_*` settings.
- **Who may call what is declared per route, in the policy, by caller class.** The classes are `page`, `browser`, `internal`, `service`, `decoder`, `peer` and `operator`, and are recognised by network and request headers.
  - The rules are path + method, with the first match winning. A route can be served at two paths with different callers, as `sdr-manager-local` is. A route's rule lives in data, where the access matrix is generated from.
  - Every route a process serves must have a rule, or it refuses to start. CI loads every service's app and checks this.
  - A refusal is a 404, so probing can't tell a refused route from a missing one.
- **The access layer is a small ASGI middleware just inside fastapi-guard's.** fastapi-guard looks up its own middleware by exact class, so a subclass would lose its lifespan warm-up, status route and WebSocket support. Its check pipeline is fixed and runs its auth checks before any hook, so a hook would answer 401 where access answers 404. Inside it, the access layer sees fastapi-guard's resolved client address, and fastapi-guard sees its 404s for the scanner ban rule. fastapi-guard's auth decorators are wired, but off in the shipped policy, for the same 401-versus-404 reason.
- **Fix the client address.** The gateway gets a fixed address on a pinned network, and it is the only proxy believed. Every uvicorn runs with `--no-proxy-headers`, as fastapi-guard requires.
- **Shared state in Redis.** It runs on a network only the FastAPI services join (decoders parse untrusted RF and must not be able to lift their own ban), with one ACL user limited to the guard's keys, generated by `service-credentials`. It fails open: an outage lets requests through. Sentinel also makes fastapi-guard's behaviour tracker fail open, because upstream it raises when Redis is down.
- **Enforcing by default, with limits sized to real traffic.** The defaults are 1200 requests a minute per address, unlimited map tiles and decoder events, and tighter limits on costly routes. Two settings let refusals be watched before they bite: `GUARD_PASSIVE_MODE` and `GUARD_ACCESS_ENFORCEMENT=log`.
- **Online features are wired and off.** These are country rules (IPInfo), cloud-provider blocking, the hosted Guard Core agent and dynamic rules, OpenTelemetry/Logfire, CORS and HTTPS/HSTS. Sentinel is offline-capable and LAN-first, so nothing reaches the internet until a token or flag is set.
- **Untrusted RF text is never scanned.** Decoder ingest bodies are written by anyone with a transmitter, so scanning them would let a hostile packet get the decoder banned.

## Consequences

- **A new endpoint needs a rule** in the policy, and the access matrix must be regenerated, or the service won't start and CI fails.
- **The compose network's subnet is pinned.** An existing deployment recreates its network once (`docker compose down`).
- **A radio host must list the core host** in `GUARD_SERVICE_HOSTS`, and core must list radio hosts the same way.
- **Docker Desktop hides client addresses.** Every client appears as one address, so per-client limits and bans are coarse there. Linux deployments see real addresses.
- **The `browser` class rejects requests without Fetch Metadata.** That stops scripts and other websites using the API, at the cost of very old browsers, and any script that needs the API must send it as the full-stack e2e suite does.
- **Some code depends on fastapi-guard internals.** That is the fail-open wrapper and the WebSocket check, so the dependency is pinned exactly and an upgrade is a reviewed change.
